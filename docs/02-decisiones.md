# 02 · Decisiones

Registro de decisiones del producto y de la arquitectura. Cada entrada: qué se
decidió y por qué. **Si una vuelta del ralph loop necesita cambiar una decisión,
añade una entrada nueva al final con la fecha y el motivo; no reescribas las
anteriores.**

## Producto (31 oct 2026)

| Decisión | Motivo |
| --- | --- |
| Nombre del producto y del ejecutable: **LumeArt** / `lumeart` | Familia Lume (LumeDB ya existe) |
| Un **único ejecutable** para Linux, Windows y macOS, sin dependencias de sistema que instalar | Requisito principal del usuario |
| **Ventana nativa** con `eframe`/`egui` | El usuario la quiere. egui compila dentro del binario; solo usa librerías gráficas que trae cualquier escritorio. Alternativa descartada: vista web (wry/Tauri) porque en Linux exige WebKitGTK instalado |
| La ventana **es el studio**: lienzo, agente y paneles viven en la app | Sustituye al studio web de pxcli |
| **Primera versión: pixel art.** Animación y vector, después | Prioridad del usuario |
| **Agente multiproveedor**: `claude -p` (suscripción), API de Anthropic, API de OpenAI; después modelos locales (Qwen…) vía servidores compatibles con OpenAI (Ollama, LM Studio, llama.cpp) | El usuario elige modelo y clave |
| **JavaScript sigue siendo el lenguaje de `anim.js` y `dibujo.js`**, con QuickJS embebido (`rquickjs`) | Reutiliza `lib.js`, `prelude.js`, prompts y los dibujos guardados |
| **Diseño antes que código**: la UI está diseñada (`docs/diseno/`) | Petición del usuario |
| Marca: icono **bombilla con paleta**, degradado **verde** (#3DBE6B), casquillo azul oscuro; misma línea que LumeDB (naranja) | Elegido por el usuario entre 6 símbolos y 6 colores |
| Acento de la interfaz: el verde de la marca (#3DBE6B); los avisos siguen en ámbar | Coherencia con la marca |
| **Compatibilidad con pxcli**: mismos comandos, argumentos, salidas y códigos de error | Los prompts y agentes existentes funcionan cambiando `pxcli` por `lumeart` |

## Sustitución de dependencias de pxcli

| En pxcli | En LumeArt | Queda en el binario |
| --- | --- | --- |
| Chrome/Chromium headless (SVG→PNG, 13 usos) | `resvg` + `tiny-skia` | Sí |
| goja (JS en Go) | `rquickjs` (QuickJS estático, con interrupción por tiempo). Alternativa: `boa_engine` (Rust puro, más lento) | Sí |
| Socket Unix + `setsid` + señales | HTTP local con `axum` en `127.0.0.1`, puerto libre + token en un archivo de estado (`directories`) | Sí |
| Ebiten (ventana) | `eframe`/`egui` | Sí |
| VectorCraft (opcional) | Calco con `vtracer`; PDF/.ai con `svg2pdf`. Lo demás (3D, `fx`, .eps, .vectorcraft) queda como plugin externo opcional | En parte |
| CLI `claude` | Sigue siendo externo y opcional (un proveedor más) | No |
| Cobra / PNG / JSON / SSE / `go:embed` | `clap` / `image` o `png` / `serde_json` / `axum` / `include_str!` o `rust-embed` | Sí |

## Bucle de refinado (ralph loop del producto)

| Decisión | Motivo |
| --- | --- |
| El bucle es un componente propio, `RefineLoop` en `lume-agent`, no el plugin `ralph-wiggum` | Funciona con todos los proveedores y no depende de nada instalado |
| **Cada vuelta empieza con el contexto vacío** (`ContextPolicy::Fresh` por defecto) | Es la clave de Ralph. El plugin oficial NO lo hace (sigue en la misma sesión); el Ralph original y el `ralph.sh` del prototipo sí |
| Entre vueltas solo pasa lo guardado en el documento: objetivo, lienzo, `notas.md`, fallos de comprobaciones y del crítico, receta | Memoria en archivos, no en la conversación |
| Terminar exige promesa **y** comprobaciones objetivas (`CompletionPolicy`) | El plugin solo busca el texto de la promesa |
| El crítico es una comprobación más del bucle | Unifica el bucle de revisión de pxcli (2 rondas fijas) |
| Límites: vueltas (8 por defecto), tokens, sin progreso (2 vueltas casi sin cambios), Detener | Coste y seguridad |
| `lumeart eval` compara: A plugin oficial, B `RefineLoop` contexto vacío, C misma conversación. B queda por defecto solo si gana a A en comparación ciega | No se puede saber de antemano cuál es mejor |

## Uso desde otros agentes

| Decisión | Motivo |
| --- | --- |
| Servidor MCP `lumeart mcp` (stdio, crate `rmcp`) en el mismo binario | Herramientas tipadas y respuestas con imagen para Claude Code, Codex y otros |
| Skill `lumeart` en el formato abierto Agent Skills (`SKILL.md`) | Hace que el agente la use solo cuando necesita arte. Claude Code: `~/.claude/skills/`; Codex: `~/.agents/skills/` |

| `lumeart.toml` en la carpeta del juego como guía de arte | Coherencia entre recursos |

| Decisión | Motivo |

| Se construye con un ralph loop (`ralph.sh`) sobre `tasks.md`, una tarea por vuelta, contexto vacío en cada vuelta | Mismo método que el prototipo |
| Identificadores de código (tipos, funciones, variables) en inglés; comentarios, documentación, textos de la UI y mensajes de commit en español | La UI y los docs del prototipo están en español |
| Edición 2024 de Rust, toolchain estable | Actual |

## Durante la construcción

| Fecha | Decisión | Motivo |
| --- | --- | --- |
| 31 oct 2026 | Mensaje de `out_of_bounds` = el del código de pxcli: `pixel (x,y) outside canvas` (y `rect (x,y) size WxH outside canvas` en `fill_rect`), no `x must be >= 0` | El `prd.md` de pxcli decía `x must be >= 0`, pero `internal/canvas/canvas.go` responde con `pixel (x,y) outside canvas`; lo que hace pxcli es lo correcto |
| 31 oct 2026 | El `Canvas` acepta de 1 a 512 de ancho y alto en todas partes (`MAX_CANVAS_SIZE`). Por debajo de 1: `canvas dimensions must be positive`; por encima de 512: `width and height must be between 1 and 512` | pxcli solo limitaba a 512 en `new`; `start --size` no tenía tope. Un único límite en el dominio es más simple y evita lienzos enormes |
| 31 oct 2026 | Coordenadas de entrada del dominio como `i64` (el `int` de Go), no `u32` | Así las coordenadas negativas llegan al lienzo y dan `out_of_bounds` con el mensaje de pxcli, en el mismo orden de validación |
| 31 oct 2026 | `Command::Resize` conserva el contenido anclado arriba a la izquierda (recorta o amplía con transparente); el `Patch` guarda las celdas recortadas para deshacer. `new WxH` del protocolo sigue siendo «lienzo nuevo en blanco y sin historial» | Un cambio de tamaño que borra el dibujo no sirve en el editor; `new` mantiene la conducta de pxcli |
| 31 oct 2026 | `Command::Batch` es atómico (si un comando falla, se revierte lo aplicado). El `batch` del protocolo (aplica los válidos y termina con `batch: N ok, M failed`) se implementa con una transacción del historial, no con `Command::Batch` | Un `Command` debe dejar el lienzo como estaba si falla; la conducta parcial de pxcli es propia del protocolo |
| 31 oct 2026 | Cada comando aplicado con éxito es un paso de deshacer aunque no cambie nada (patch vacío); un comando que falla no deja paso ni vacía la pila de rehacer | Es lo que hace `history.Apply` de pxcli: `set_pixel 0 0 red` dos veces y `undo` deja el píxel en rojo |
| 31 oct 2026 | `History::undo_run(run)` deshace los últimos pasos **seguidos** de esa ejecución del agente; si el último paso es de otro autor, no deshace nada (`no_history`) | Deshacer pasos intercalados con los del usuario fuera de orden podría corromper el lienzo |
| 31 oct 2026 | Comando nuevo del protocolo `resize <w> <h>` (solo LumeArt) para `Command::Resize`; pxcli respondería `unknown command` | La receta debe poder escribir todos los comandos en texto; añadir un comando no rompe a los clientes de pxcli |
| 31 oct 2026 | `export` valida la escala (1–64) al parsear, no al exportar | En pxcli no hay ninguna comprobación entre parsear y validar la escala, así que la respuesta es la misma y el dominio no necesita E/S |
| 31 oct 2026 | Dentro de una transacción, `undo` deshace solo el último comando (y `redo` lo devuelve a la transacción); al cerrarla, lo que quede es un solo paso. Sustituye a «`undo` cierra la transacción abierta» de la vuelta anterior | En pxcli cada línea de un `batch` era un paso aparte: `a; b; undo` deshacía solo `b`. Así el `batch` de LumeArt da la misma salida que pxcli y además se deshace entero después |
| 31 oct 2026 | El `batch` vive en el dominio (`run_batch`) y no en la CLI; la ruta de `export` se resuelve con una función que pasa quien llama (la CLI enviará su carpeta de trabajo) | La CLI de LumeArt es un cliente HTTP: el `batch` debe ejecutarse junto al documento para ser un paso de deshacer. El dominio no puede leer la carpeta actual |
| 31 oct 2026 | En un `batch` también se acepta `lumeart` (y `…/lumeart`) al principio de la línea, además de `pxcli` | Los agentes escribirán `lumeart set_pixel …` |
| 31 oct 2026 | La `Recipe` la mantiene el `History` (aplicar añade, deshacer quita, rehacer repone, `new` vacía) y guarda comandos simples: un `Batch` se aplana. El texto usa colores canónicos `#rrggbbaa` (pxcli copiaba el argumento tal cual: `red`, `#f00`) | Así la receta nunca se desincroniza del deshacer, también con transacciones; los colores canónicos dan el mismo dibujo |
| 31 oct 2026 | `Palette::from_canvas` excluye todo color con opacidad 0, no solo `#00000000` | Es lo que hace `palette()` en `internal/anim/check.go` de pxcli: un píxel invisible no es un color del dibujo |
| 31 oct 2026 | La `Recipe` guarda su tamaño de partida (`start`: el lienzo en blanco del que parte). `new W H` lo fija; volver a una versión lo restaura con la receta. En `.lume` irá en `manifest.json` (el texto de la receta sigue siendo el de pxcli) | Una versión debe poder reconstruirse sola, también si entre versiones hubo un `new` de otro tamaño |
| 31 oct 2026 | Volver a una versión es un paso del historial que sustituye lienzo (con `Patch::between`) y receta enteros (`HistoryEntry.recipe_swap`); se deshace en un paso | Criterio de T:10 y coherencia: deshacer siempre devuelve lienzo y receta a la vez |
| 31 oct 2026 | Comparar versiones de distinto tamaño compara el área que cubren entre las dos; lo que queda fuera de una cuenta como transparente | Es lo que se ve al superponerlas en la interfaz |
| 31 oct 2026 | Los PNG se escriben en RGBA de 8 bits **sin premultiplicar**: el color guardado es el que sale. pxcli escribía mal los píxeles semitransparentes (Go trataba `#cfdde3aa` como premultiplicado y lo guardaba como `#374c55aa`); `lume_store::png_io::pxcli_png_color` reproduce ese fallo solo para comparar con los `final.png` de pxcli | Un PNG correcto es lo que espera cualquier motor de juego; `get_pixel` ya devolvía el color sin alterar en pxcli, así que el protocolo no cambia |
| 31 oct 2026 | Mensajes de error de archivo al estilo de Go (`open <ruta>: no such file or directory`) | Compatibilidad con las salidas de pxcli |
| 31 oct 2026 | `.lume` formato 1: `manifest.json` (`format`, `app`, `name`, `width`, `height`, `recipe_start`, `palette`, `actions`, `versions` con `author`/`run`/`message`/`recipe_start`), `canvas.png`, `recipe.txt`, `notas.md`, `versions/NNN.png` y `.txt`. El historial de deshacer no se guarda. El formato 0 es el borrador de `docs/03-arquitectura.md` (`size: "WxH"`), solo para tener una migración real | Legible con cualquier herramienta (comprobado con `unzip -t` y `zipfile` de Python); la migración queda encadenada para formatos futuros |
| 31 oct 2026 | `zip` 2.4 con solo `deflate` (Rust puro, `flate2` + `miniz_oxide` + `zopfli`), no 8.x | `zip` 8 exige Rust 1.88 y el workspace declara 1.85; sin `bzip2`/`zstd`/`lzma`, que enlazan C |
| 31 oct 2026 | Importar una carpeta de pxcli: si la receta (desde el tamaño de `meta.json`) reproduce `final.png` tal como lo escribía pxcli, el lienzo es el de la receta (colores semitransparentes correctos); si no, manda `final.png` y la receta queda sin tamaño de partida. El encargo de `meta.json` va a `notas.md` | Las 16 ejecuciones de `reference/runs` se reproducen así exactamente |
| 31 oct 2026 | Los puertos asíncronos (`ModelProvider`, `AgentRunner`, `AgentTools`) devuelven `BoxFuture` en vez de usar `async-trait`; `CancellationToken` de `tokio-util` | Así se usan como `dyn Trait` sin otra macro; `tokio-util` es Rust puro |
| 31 oct 2026 | Un solo `PortError` (mensajes en español, se muestran al usuario) para todos los puertos salvo `DocumentStore`, que usa `DomainError` con los códigos del protocolo | `export` responde en el protocolo de pxcli; los demás puertos hablan con la interfaz |
| 31 oct 2026 | Las claves viajan como `Secret` (sin `Display` y con `Debug` = `Secret(****)`) | Que una clave no pueda acabar en un log por descuido |
| 31 oct 2026 | API: `POST /v1/commands` ejecuta cada línea por separado (una respuesta del protocolo por línea, como el daemon de pxcli); con `?batch=1` es un `batch` (un paso de deshacer, salida de `pxcli batch`, cabecera `x-lumeart-failed`). La carpeta del cliente va en `?cwd=` | La CLI necesita las dos formas: `lumeart set_pixel …` y `lumeart batch …` |
| 31 oct 2026 | Archivo de estado `session.json` (`port`, `pid`, `token`, `version`) en `<datos del usuario>/lumeart/` (`directories`), permisos 0600; el tipo `SessionInfo` está en el dominio (contrato entre API y CLI) | Sustituye a `/tmp/pxcli.sock`; el token no debe leerlo otro usuario |
| 31 oct 2026 | `DocumentStore::encode_png` en el puerto | `lume-api` sirve el PNG sin depender de `lume-store` |
| 31 oct 2026 | Un test (`server_on_loopback`) abre un puerto en 127.0.0.1; el resto llama al `Router` sin sockets | «Sin red» se entiende como sin salir del equipo; el bucle local es necesario para probar el servidor de verdad |
| 31 oct 2026 | Extensión del protocolo: un argumento entre comillas dobles puede tener espacios (`export "C:\Users\Ana María\a.png" 2`; `\"` y `\\` dentro). La CLI y `batch` entrecomillan las rutas con espacios | En pxcli una ruta con espacios rompía `export`; en Windows son habituales. Una comilla antes siempre daba error, así que ninguna respuesta válida de pxcli cambia (los fixtures de compatibilidad siguen idénticos) |
| 31 oct 2026 | La CLI imprime los errores como cobra (`Error: err …` en stderr, código 1) pero sin el texto de uso que cobra añadía detrás | Los agentes leen la línea `Error:`; el uso repetido solo ensucia |
| 31 oct 2026 | Como en pxcli, las opciones van antes de los argumentos (`lumeart --session x get_pixel 0 0`); detrás, son argumentos | Permite números negativos sin comillas (`set_pixel -1 10 red`). `--socket` se acepta como alias de `--session` |
| 31 oct 2026 | La CLI usa un cliente HTTP/1.1 propio sobre `TcpStream` (solo 127.0.0.1, sin TLS) | Evita dependencias para hablar con la API local |
| 31 oct 2026 | `start` relanza el propio ejecutable con el subcomando oculto `serve`, desligado de la terminal (`process_group(0)` en Unix, `DETACHED_PROCESS` en Windows), con su salida de error en `session.log` junto al archivo de estado | Un solo binario y sin `setsid`/señales (pxcli); funciona igual en las tres plataformas |
| 31 oct 2026 | Una sesión está viva si su API contesta 200 con el token de su archivo de estado; si no, el estado es huérfano y `start`/`stop` lo borran | No hace falta comprobar PID (sin `unsafe` ni `kill`), y otro proceso en el mismo puerto no se confunde con la sesión |
